

إضافات v21 — اختبار هجومي محلي وإصلاحات ما بعد التقرير
=======================================================

نطاق الهجوم
-----------
تم تنفيذ مراجعة محلية غير مدمّرة على قواعد Firestore، مسارات رسائل الخاص، دليل القنوات، تشفير المرسل والمستلم، واجهة إشعارات المجموعة، نقاط HTML، وحدود طلبات API. لم يتم استهداف موقع منشور أو حساب حقيقي، ولم يتم حذف أو تعديل بيانات خارج نسخة المشروع.

ثغرة حرجة وُجدت وأُغلقت
------------------------
وُجد شرط قديم داخل تحقق cipher يتطلب شكل ECDH-P256-AESGCM القديم في نفس الوقت مع alg الجديد dual. هذا كان يجعل التحقق متناقضًا. أزيل الشرط القديم وأصبح schema v2 المزدوج هو الشكل المعتمد.

تقوية API الإشعارات
-------------------
أضيف رفض للطلبات الأكبر من 20KB، وقص chatId وmessageId إلى 180 حرفًا، وتنظيف وحدود قصوى لخرائط rate وdedupe حتى لا يستنزف مهاجم الذاكرة عبر UIDs أو messageIds كثيرة.

الاختبارات
----------
أُضيف security-regression.test.py. نتيجة آخر تشغيل: 21/21 اختبارًا ناجحًا، وتشمل:
- تجاوز رسالة الخاص بنص أو reply أو fwd أو صورة أو موقع خارج cipher.
- تفاعل reactions واضح في الخاص.
- حذف خاص يغير المحتوى.
- تناقض schema التشفير.
- انتحال groupDirectory وكشف members/admins.
- إشعار مجموعة بلا messageId أو برسالة لا تخص المرسل.
- تكرار messageId وselfTest والحمولة الكبيرة واستنزاف خرائط الذاكرة.
- وجود نسختي تشفير المرسل والمستقبل ومسار legacy.
- وجود شارة الموقع وحزمة الإيموجي الكبيرة.

الحدود
------
لم يمكن تشغيل Firestore Emulator دون إعداد Firebase/Java أو مشروع اختبار. لذلك الاختبارات الحالية static security regression وليست قرار Rules صادرًا من محرك Firestore. قبل الإنتاج يجب تشغيل نفس السيناريوهات على Emulator بحسابات: مالك، مشرف، عضو، غير عضو، مستخدم محظور، ومستخدم بلا email verification.

كما أن rate/dedupe داخل ذاكرة العملية لا يكفي للإنتاج متعدد النسخ؛ يجب نقله إلى Redis أو Firestore transaction/Cloud Tasks مع App Check.


إضافات v22 — اختبار Firebase Emulator فعلي
============================================

تم تشغيل Firebase Firestore Emulator محليًا باستخدام Java 21 وFirebase CLI 15.32.1. فاحص الأقواس الحقيقي وجد القوس الزائد في شرط السطر 112 وتم حذفه. بعد الإصلاح أصبحت الأقواس متوازنة، وبدأ المحاكي بتحميل firestore.rules.

تم تشغيل Rules Unit Testing بحسابات وهمية:
- owner: مالك موثق بالبريد.
- member: عضو.
- outsider: غير عضو.

النتيجة: 9/9 اختبارات فعلية ناجحة:
1. غير العضو لا يقرأ المجموعة الخاصة.
2. العضو يقرأ مستند المجموعة.
3. غير العضو لا يقرأ رسائل المجموعة.
4. الدليل غير الحساس يمكن قراءته بدون members/admins.
5. رسالة الخاص plaintext مرفوضة.
6. ciphertext dual الصحيح مقبول.
7. reaction واضح في الخاص مرفوض.
8. إنشاء دليل وهمي بلا مجموعة حقيقية مرفوض.
9. إنشاء المجموعة ودليلها في batch واحدة مقبول.

ملاحظة المحاكي: بعض عمليات الرفض تظهر في سجل المحاكي كـ PERMISSION_DENIED مع evaluation error داخلي أثناء تجربة فروع Rules التي تصل إلى حقول غير موجودة؛ النتيجة الأمنية نفسها رفض صحيح، لكن يفضل لاحقًا تبسيط هذه الفروع لتقليل ضوضاء السجل. لا يوجد قبول غير مصرح به في الاختبارات التسعة.

تظل مراجعة self-ECDH الثابتة مؤجلة: نسخة المرسل الحالية تستخدم identity key ثابتة، وهذا لا يحقق forward secrecy كاملًا. إصلاحه بشكل صحيح يتطلب تخزين sender ephemeral private key محليًا مرتبطًا بمعرّف الرسالة، وليس مجرد تبديل الحقل في Firestore.
